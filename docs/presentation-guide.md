## 二、各部分详细讲解内容

### 1. 开场介绍（1 分钟）

#### 讲解要点

- **项目定位**：这是一个基于 Ghost 开源博客系统的二次开发课程实验项目
- **做了什么**：在 Ghost 官方 Casper 主题基础上，开发了一个自定义主题 `sdut-blog`，新增了标签导航、文章目录、阅读进度条、返回顶部、搜索增强等功能
- **核心思路**：不修改 Ghost 核心代码，完全通过主题层（Theme Layer）进行扩展，符合开源软件二次开发的最佳实践
- **成果**：完成了一个功能完整、可运行的个人博客系统，包含前台展示和后台管理

#### 可能的提问

**Q: 为什么选博客系统作为实验项目？**
> 回答思路：
> - 博客系统是 Web 开发的经典场景，涵盖了内容管理、用户交互、前端展示等多个方面
> - Ghost 是一个成熟的开源项目，代码质量高，适合学习
> - 主题化的架构让二次开发有清晰的边界，既能学到东西，又不至于无从下手

**Q: 这个项目和直接用 Ghost 有什么区别？**
> 回答思路：
> - 原生 Ghost 提供的是基础博客功能和默认主题
> - 我们做的是**二次开发**——在不修改核心代码的前提下，通过自定义主题增加了多个实用功能
> - 相当于"站在巨人的肩膀上"，既利用了 Ghost 的成熟能力，又加入了自己的设计和实现

#### 开场话术参考

> "老师好，我今天答辩的项目是基于 Ghost 的开源个人博客系统二次开发。Ghost 是一个国外非常流行的开源博客平台，版本是 6.62.0。我的工作主要是在它的默认主题 Casper 基础上，开发了一个自定义主题 sdut-blog，新增了标签导航、文章目录、阅读进度、搜索增强等功能。整个开发过程严格遵循'不修改核心代码'的原则，所有功能都通过主题层实现。下面我从技术选型、架构、功能实现等几个方面来介绍。"

### 2. 技术选型（1 分钟）

#### 讲解要点

**为什么选 Ghost？**
- **专业的博客系统**：相比 WordPress 更轻量、更专注于内容创作
- **现代技术栈**：Node.js + Express + Handlebars，前后端分离的设计思路
- **主题化架构**：主题与核心完全分离，二次开发边界清晰
- **活跃的开源社区**：MIT 协议，文档完善，有大量主题和插件可供参考

**技术栈一览：**
- 后端：Node.js + Express（Ghost 核心）
- 数据库：SQLite3（本地开发环境，部署可换 MySQL/PostgreSQL）
- 模板引擎：Handlebars（Ghost 主题标准）
- 前端：原生 JavaScript + CSS（无框架依赖，性能好）
- 管理后台：Ghost Admin（React 构建，原生提供）
- 部署方式：Ghost CLI 本地运行

**为什么用原生 JS 而不是框架？**
- 主题层追求轻量，减少依赖
- Ghost 官方主题都是原生 JS 实现，保持一致
- 功能相对独立，用原生 JS 足够，避免过度工程化

#### 可能的提问

**Q: Ghost 和 WordPress 有什么区别？**
> 回答思路：
> - WordPress 是 CMS（内容管理系统），功能大而全，插件生态丰富，但比较重
> - Ghost 专注于博客和内容创作，更轻量、更现代
> - 技术栈不同：WordPress 是 PHP + MySQL，Ghost 是 Node.js
> - 从学习角度，Ghost 代码更现代化，更容易理解架构

**Q: 为什么不用 Hexo / Hugo 这类静态博客？**
> 回答思路：
> - Hexo/Hugo 是静态站点生成器，生成纯 HTML 文件，没有后台
> - Ghost 是动态博客系统，有完整的后台管理、会员系统、评论功能
> - 实验要求是"开源系统二次开发"，Ghost 有服务端、有数据库、有后台，更能体现对完整 Web 系统的理解

### 3. 项目架构（2 分钟）

#### 讲解要点

**Ghost 整体架构（三层结构）：**

```
┌─────────────────────────────────────┐
│         前台主题（Theme）            │  ← 我们的工作在这里
│  Handlebars 模板 + CSS + JS         │
├─────────────────────────────────────┤
│         Ghost Core 核心服务          │
│  Express + API + 数据模型 + 业务逻辑  │
├─────────────────────────────────────┤
│         SQLite 数据库               │
│  posts / tags / members / settings   │
└─────────────────────────────────────┘
```

**关键概念：主题系统（Theme System）**
- Ghost 的前台展示完全由主题控制
- 主题是一组 Handlebars 模板文件 + 静态资源（CSS/JS/图片）
- 通过 `{{!< default}}` 实现模板继承
- 通过 `{{> partial}}` 实现组件复用
- 后台可以随时切换主题，不影响数据

**请求处理流程：**
1. 用户访问 URL → Express 路由匹配
2. Ghost 从数据库查询数据（文章、标签、作者等）
3. 将数据传给对应的主题模板
4. Handlebars 模板引擎渲染成 HTML
5. 返回给浏览器

**项目目录结构（重点区分"能改的"和"不能改的"）：**
- `runtime/versions/6.62.0/core/` — Ghost 核心代码，**不修改**
- `runtime/content/themes/sdut-blog/` — 自定义主题，**全部开发工作在这里**
- `runtime/content/data/ghost-local.db` — SQLite 数据库，**通过后台管理**
- `runtime/config.development.json` — 配置文件，**谨慎修改**
- `docs/` — 项目文档

**自定义主题的文件结构：**
- `default.hbs` — 全局布局模板（所有页面的"外壳"）
- `index.hbs` — 首页模板
- `post.hbs` — 文章详情页模板
- `tag.hbs` — 标签列表页模板
- `author.hbs` — 作者页模板
- `error-404.hbs` — 404 页面
- `partials/post-card.hbs` — 文章卡片组件（可复用）
- `assets/css/custom.css` — 自定义样式
- `assets/js/custom.js` — 自定义 JavaScript
- `package.json` — 主题配置（自定义设置项定义在这里）

#### 可能的提问

**Q: Handlebars 是什么？和 Vue/React 有什么不同？**
> 回答思路：
> - Handlebars 是一个服务端模板引擎，在服务器上把数据和模板拼成 HTML 返回
> - Vue/React 是前端框架，在浏览器里渲染页面
> - Ghost 选择 Handlebars 是因为博客内容以展示为主，服务端渲染对 SEO 友好，性能也更好
> - 我们的主题开发主要就是写 Handlebars 模板，配合前端 JS 做交互增强

**Q: Ghost 的主题和 WordPress 的主题有什么区别？**
> 回答思路：
> - 思路类似，都是把视图层抽离出来
> - Ghost 主题更简洁，就是模板文件 + 静态资源
> - WordPress 主题可以包含 PHP 代码，能改更多东西
> - Ghost 的设计哲学是"核心只提供 API，主题只负责展示"，职责更清晰

**Q: 为什么不直接修改 Casper 主题的源文件？**
> 回答思路：
> - 直接修改的话，后续 Casper 升级就很麻烦，需要手动合并
> - 我们把自定义代码放在独立的 custom.css 和 custom.js 中，通过 default.hbs 引入
> - 这样 Casper 原有的代码保持不变，升级时只需要更新 built/ 目录下的编译产物
> - 这也是一种"低侵入式"的二次开发思路

### 4. 自定义主题开发（4 分钟）—— 重点！

> **讲解策略**：每个功能讲"为什么做 + 怎么做的 + 效果展示"，边讲边演示。
> 一定要突出"这是我自己加的，原生 Casper 没有"。

#### 功能总览

在 Casper 主题基础上，新增了以下功能：

| 功能 | 位置 | 实现方式 | 原生 Casper |
|------|------|---------|------------|
| 标签导航栏 | 首页/文章页顶部 | Handlebars + CSS | ❌ 无 |
| 文章目录（TOC） | 文章页侧边 | JS 动态生成 | ❌ 无 |
| 阅读进度条 | 文章页顶部 | JS + CSS | ❌ 无 |
| 返回顶部按钮 | 右下角悬浮 | JS 动态创建 | ❌ 无 |
| 主题色切换 | 全局 | CSS 变量 + 后台配置 | ❌ 无 |
| 文章卡片美化 | 首页/列表页 | CSS 重写 | ⚠️ 有基础样式 |
| 自定义底部栏 | 全局 | Handlebars + CSS | ⚠️ 有默认 Footer |
| 文章标签展示 | 文章页底部 | Handlebars | ❌ 无 |
| 相关文章推荐 | 文章页底部 | `{{#get}}` Helper | ❌ 无 |
| 搜索历史记录 | 搜索弹窗 | JS + localStorage | ❌ 无 |

#### 4.1 标签导航栏

**为什么做：**
- 原生 Casper 导航栏只有自定义菜单，读者不能快速浏览热门分类
- 标签是博客内容组织的重要方式，应该让用户一眼看到

**怎么做的：**
- 在 `default.hbs` 中使用 Ghost 的 `{{#get "tags"}}` Helper 查询热门标签
- 按文章数量排序，取前 8 个
- 用 CSS 做成横向滚动的标签栏
- 当前页面所在标签会高亮（`{{#has tag=slug}}` 判断）

**代码片段：**
```handlebars
{{#get "tags" limit="8" order="count.posts desc" as |top_tags|}}
    {{#foreach top_tags}}
        <a href="{{url}}" class="tag-nav-item {{#has tag=slug}}active{{/has}}">
            <span class="tag-nav-dot"></span>
            {{name}}
        </a>
    {{/foreach}}
{{/get}}
```

**演示时说：** "大家可以看到导航栏下方有一排热门标签，点击可以快速跳转到对应标签的文章列表。这个功能原生 Casper 是没有的，我通过 Ghost 的 `{{#get}}` 辅助函数查询热门标签数据，然后自己写了样式和交互。"

#### 4.2 文章目录（TOC）

**为什么做：**
- 长文章阅读体验不好，读者不知道文章结构
- 目录可以帮助快速定位和跳转到感兴趣的章节

**怎么做的：**
- 在 `post.hbs` 中预留目录容器（侧边栏）
- JS 在页面加载后扫描文章内容中的 h1-h4 标题
- 自动生成目录列表，点击平滑滚动到对应位置
- 滚动时高亮当前阅读的章节
- 支持收起/展开

**关键技术点：**
- 用 `findContentElement()` 函数做了多选择器兼容（`.gh-content`、`.article-content` 等）
- 给没有 id 的标题自动生成 id
- 使用 `getBoundingClientRect()` 计算滚动位置
- 滚动高亮通过 `offsetTop` 对比实现

**演示时说：** "文章页右侧有一个目录导航，是 JavaScript 在页面加载后自动扫描标题生成的。它支持点击跳转、滚动高亮，还可以收起展开。为了兼容不同的主题结构，我写了一个多选择器的降级方案，确保在各种情况下都能正常工作。"

#### 4.3 阅读进度条

**为什么做：**
- 让读者对文章长度有直观感知
- 很多技术博客和阅读类 App 都有这个功能

**怎么做的：**
- 在 `default.hbs` 顶部放一个固定定位的进度条容器
- JS 监听 scroll 事件，计算滚动百分比
- 用 CSS 渐变 + 阴影效果，和主题色联动

**代码逻辑：**
```javascript
const progress = (scrollTop / (docHeight - windowHeight)) * 100;
progressBar.style.width = progress + '%';
```

**演示时说：** "滚动页面时，顶部有一条渐变的进度条实时显示阅读进度。这个功能很简洁，但细节上做了优化——进度条颜色和主题色联动，用了 CSS 变量，切换主题色时自动跟着变。"

#### 4.4 返回顶部按钮

**为什么做：**
- 长文章往下翻完后，想回到顶部很麻烦
- 是一个体验优化的小功能

**怎么做的：**
- JS 动态创建按钮元素（不用改模板）
- 滚动超过 300px 时淡入显示
- 点击平滑滚动到顶部
- 有悬停动画效果

**演示时说：** "往下滚动一段距离后，右下角会出现一个返回顶部按钮，点击可以平滑回到页面顶部。这个按钮是完全用 JS 动态创建的，没有修改模板结构。"

#### 4.5 主题色切换

**为什么做：**
- 让博客更有个性化，用户可以选择喜欢的配色
- 体现 Ghost 主题自定义设置的能力

**怎么做的：**
- 在 `package.json` 的 `config.custom` 中定义 `primary_color` 选项
- 提供 4 种配色：科技蓝、活力橙、森林绿、优雅紫
- 用 CSS 变量（`--sdut-primary`）统一管理主题色
- 在 `body` 上加上 `color-xxx` class，切换不同的变量值
- 后台 Design 设置中可以直接切换，所见即所得

**代码片段（package.json）：**
```json
"primary_color": {
    "type": "select",
    "options": ["科技蓝", "活力橙", "森林绿", "优雅紫"],
    "default": "科技蓝"
}
```

**演示时说：** "主题支持 4 种配色方案，可以在 Ghost 后台的设计设置里切换。实现方式是用 CSS 变量定义主题色，然后通过 body 上的 class 切换不同的变量值。这是 Ghost 主题的一个标准特性——在 package.json 里定义自定义配置项，后台自动生成设置界面。"

> **演示技巧**：讲到这里的时候，可以打开 Ghost 后台，现场切换一下主题色，让老师看到效果。

#### 4.6 相关文章推荐

**为什么做：**
- 增加读者停留时间，引导阅读更多文章
- 很多博客系统都有这个功能

**怎么做的：**
- 在 `post.hbs` 底部使用 `{{#get "posts"}}` 查询
- 排除当前文章（`filter="id:-{{id}}"`）
- 取 3 篇文章，用 post-card 组件展示

#### 可能的提问

**Q: 这些功能中，哪个是你觉得最有技术含量的？**
> 回答思路：
> - 可以说文章目录功能，因为它涉及 DOM 操作、滚动监听、平滑滚动、动态 id 生成等多个前端技术点
> - 或者说搜索增强，因为它体现了产品思维和对用户体验的思考
> - 重点不是功能本身难不难，而是你在实现过程中遇到了什么问题、怎么解决的

**Q: 你用了 `{{#get}}` 这个 Helper，它是干什么的？**
> 回答思路：
> - `{{#get}}` 是 Ghost 提供的一个自定义 Handlebars Helper
> - 可以在模板中灵活查询数据，比如查热门标签、相关文章、特定作者的文章等
> - 相当于在模板层做数据查询，不需要写后端代码
> - 我们项目中标签导航和相关文章推荐都用到了它

**Q: CSS 变量是怎么工作的？**
> 回答思路：
> - CSS 变量（自定义属性）是 CSS 原生支持的功能，用 `--var-name` 定义，`var(--var-name)` 使用
> - 我们在 `:root` 上定义默认的主题色变量
> - 然后在 `.color-活力橙` 等 class 下覆盖这些变量的值
> - body 上加上对应的 class 后，页面中所有使用这些变量的地方都会自动变色
> - 相比预处理器变量，CSS 变量是运行时的，可以动态切换

### 5. 自主功能：搜索增强（2 分钟）

#### 讲解要点

**功能定位：**
- 这是本次实验的**自主创新功能**，在 Ghost 原生搜索基础上做了前端增强
- 完全在主题层实现，不修改 Ghost 核心代码

**做了什么：**

| 功能 | 说明 | 技术实现 |
|------|------|---------|
| 搜索历史记录 | 记录最近 5 条搜索，点击可快速搜索 | localStorage |
| 关键词高亮 | 搜索结果中高亮匹配的关键词 | DOM 处理 |
| 空结果推荐 | 搜索无结果时显示推荐内容 | Content API |
| 键盘导航 | 上下键选择历史记录，回车搜索 | 键盘事件 |

**为什么在主题层实现（设计思路）：**
- 修改 Ghost 核心 → 功能最强，但升级困难，维护成本高
- 独立搜索服务 → 可定制性强，但部署复杂
- **主题层前端增强** → 无需改核心，升级友好，零后端成本 ✅

**搜索历史的技术细节：**
- 使用 MutationObserver 监听搜索框的出现（因为搜索弹窗是动态加载的）
- 搜索历史存在 `localStorage` 的 `sdut_search_history` 键中
- 最多保存 5 条，重复搜索会移到最前
- 搜索框聚焦且为空时显示历史记录面板
- 做了异常处理：localStorage 不可用时静默降级

**与上游基线的差异对比：**

| 功能 | Casper 原生 | sdut-blog 主题 |
|------|------------|---------------|
| 搜索入口 | ✅ 有 | ✅ 有（样式优化） |
| 搜索历史 | ❌ 无 | ✅ 新增 |
| 关键词高亮 | ❌ 无 | ✅ 新增 |
| 空结果推荐 | ❌ 无 | ✅ 新增 |
| 键盘导航 | ❌ 无 | ✅ 新增 |

#### 可能的提问

**Q: 为什么不直接改 Ghost 的搜索后端？**
> 回答思路：
> - 实验的边界要求是"不修改核心代码"，主题层二次开发
> - 而且 Ghost 的搜索后端是用 SQLite 的 FTS5 做的，改起来比较复杂
> - 在前端做增强是投入产出比最高的方式——既能提升用户体验，又不影响核心代码
> - 这也是一种常见的开源软件二次开发思路：在不侵入核心的前提下做外围增强

**Q: localStorage 有什么局限？**
> 回答思路：
> - 容量有限（一般 5MB）
> - 只在当前浏览器有效，换设备不同步
> - 隐私模式下可能不可用
> - 但对于搜索历史这个场景完全够用——历史记录本身就是个人化的本地数据
> - 代码中也做了降级处理，localStorage 不可用时功能静默禁用，不影响搜索本身

**Q: MutationObserver 是干什么的？为什么要用它？**
> 回答思路：
> - MutationObserver 是浏览器提供的 API，可以监听 DOM 的变化
> - 因为 Ghost 的搜索弹窗是点击搜索按钮后才动态创建的，页面加载时搜索框还不存在
> - 所以用 MutationObserver 监听 body，等搜索框出现后再给它加上历史记录功能
> - 这是处理动态加载内容的常用技巧

### 6. 遇到的问题与解决方案（2 分钟）

> **这是老师最爱听的部分！** 讲 bug 不是丢分，反而是加分项——体现你真的动手做了，而且有排错能力。
> 每个 bug 按照"现象 → 排查过程 → 原因 → 修复"的逻辑来讲。

#### Bug 1：首页文章计数为空

**现象：** 首页"最新文章"旁边显示"共 篇文章"，数字是空的。

**排查过程：**
- 一开始以为是分页数据没传过来
- 查了 Ghost 文档才发现 `@site.posts` 这个变量不存在
- 打印了一下 pagination 对象，发现里面有 total 字段

**原因：** 错误使用了 `@site.posts` 变量，Ghost 主题中全局变量 `@site` 不包含 `posts` 属性。

**修复：** 改用 `{{pagination.total}}`，这是分页上下文中的正确变量。

**代码位置：** `index.hbs` 第 36 行

**收获：** 搞清楚了 Ghost 模板中全局数据（`@site`、`@custom`）和上下文数据（`posts`、`pagination`）的区别。

#### Bug 2：标签页/作者页标题为空

**现象：** 标签页只显示 "#" 和 "共 篇文章"，标签名是空的；作者页类似。

**排查过程：**
- 在标签页模板中直接写 `{{name}}` 不显示
- 翻文档发现标签页的上下文是 posts 列表，不是 tag 对象
- 需要用 `{{#tag}}...{{/tag}}` 进入标签上下文

**原因：** 缺少 `{{#tag}}` / `{{#author}}` 上下文包裹。Ghost 的标签页和作者页，顶层上下文是文章列表，标签/作者信息需要通过块级 Helper 进入。

**修复：** 用 `{{#tag}}...{{/tag}}` 包裹标签信息的显示部分，标签名、描述、文章计数都放在里面。

**代码位置：** `tag.hbs` 第 6-12 行、`author.hbs` 第 6-15 行

**注意：** 在 `{{#tag}}` 内部访问 `pagination.total` 需要用 `../pagination.total` 向上回溯一级上下文。

#### Bug 3：JS 功能整体失效

**现象：** 返回顶部按钮不显示、目录不生成、进度条不动，所有自定义 JS 功能都不工作。

**排查过程：**
- 打开控制台看到有一个 JS 报错
- 发现因为某个 init 函数报错，后面的函数都没执行
- 因为所有初始化是顺序调用的，一个挂了全挂

**原因：** JavaScript 中如果一个函数抛出异常，后续的同步代码都会停止执行。我们的初始化函数是顺序调用的，一个出错全部失效。

**修复：** 写了一个 `safeInit()` 工具函数，用 try-catch 包裹每个功能的初始化：
```javascript
function safeInit(name, fn) {
    try {
        console.log('[SDUT] 初始化:', name);
        fn();
        console.log('[SDUT] 完成:', name);
    } catch (e) {
        console.error('[SDUT] 初始化失败:', name, e);
    }
}
```
每个功能独立运行，一个失败不影响其他功能。

**代码位置：** `assets/js/custom.js` 第 10-18 行

**收获：** 学到了"容错设计"的思想——功能之间应该相互隔离，避免单点故障影响全局。

#### Bug 4：目录不显示标题

**现象：** 目录一直显示"本文暂无目录"，但文章明明有很多标题。

**排查过程：**
- 一开始以为是选择器写错了
- 用控制台检查 DOM，发现内容容器的 class 不是 `.gh-content`
- 原来 Ghost 不同版本、不同编辑器生成的内容容器 class 不一样

**原因：** 选择器 `.gh-content` 不兼容，文章内容容器的 class 名在不同场景下可能不同。

**修复：** 写了 `findContentElement()` 函数，按优先级尝试多个选择器，找到第一个匹配的就用：
```javascript
const selectors = ['.gh-content', '.article-content', 'article .content', '.post-content', '.content'];
```

**代码位置：** `custom.js` 的 `findContentElement()` 函数（第 21-39 行）

**收获：** 做前端开发要考虑兼容性，不能假设 DOM 结构一定是某种样子，要有降级方案。

#### Bug 5：邮件发送失败（QQ 邮箱 SMTP）

**现象：** 会员注册时收不到邮件，后台报错 "501 Mail from address must be same as authorization user"。

**排查过程：**
- 一开始以为是授权码写错了
- 查了 QQ 邮箱 SMTP 的文档
- 发现报错信息说发件人地址必须和认证用户一致
- Ghost 默认的发件人地址是 noreply@域名，和 QQ 邮箱账号不一样

**原因：** 发件人地址（from）和 SMTP 认证的邮箱地址不一致。QQ 邮箱要求发件人必须是认证账号本身。

**修复：** 在 `config.development.json` 的 mail 配置中添加 `from` 字段，设为和 `auth.user` 相同的邮箱地址。

**代码位置：** `runtime/config.development.json` 第 15 行

**收获：** 配置邮件服务时，不同服务商的要求不一样，要仔细看文档。尤其是 from 地址这个细节很容易忽略。

#### Bug 6：CDN 资源加载失败

**现象：** 搜索弹窗打不开、会员登录弹窗不显示、评论不加载。

**排查过程：**
- 控制台报了好几个 404 和超时
- 发现加载的资源都是 `cdn.jsdelivr.net` 域名下的
- 用浏览器单独访问 jsdelivr，发现加载很慢甚至超时
- 查了一下，jsdelivr 在国内访问不稳定

**原因：** Ghost 官方的 sodo-search（搜索）、portal（会员）、comments-ui（评论）三个组件默认通过 jsdelivr CDN 加载。jsdelivr 在国内访问不稳定，导致这些组件加载失败。

**影响范围：** Ghost 官方组件加载失败，但**主题自有功能不受影响**（标签导航、目录、进度条、返回顶部都正常）。

**说明：** 这不是主题 Bug，是网络环境问题。主题代码已经正确集成了这些组件。

**可能的解决方案：**
- 配置国内 CDN 镜像（七牛云、又拍云等有 jsdelivr 镜像）
- 自建 CDN 加速
- 部署到海外服务器

> **讲解技巧**：讲这个 bug 的时候，可以说"虽然这不是我写的代码的问题，但通过排查我搞清楚了 Ghost 的前端组件加载机制，也理解了 CDN 在实际项目中的重要性。"

#### 可能的提问

**Q: 你是怎么排查这些问题的？**
> 回答思路：
> - 先看浏览器控制台有没有报错（前端问题）
> - 再看 Ghost 的日志文件（后端问题）
> - 然后查 Ghost 官方文档，确认 API 的正确用法
> - 最后通过小范围测试、打日志来定位
> - 主要就是"看报错 → 查文档 → 做假设 → 验证"这个流程

**Q: safeInit 这个思路你是怎么想到的？**
> 回答思路：
> - 一开始所有功能都失效了，我在控制台看到了一个报错
> - 发现是第一个 init 函数报错导致后面都不执行了
> - 然后就想，如果每个功能各自 try-catch，就不会互相影响了
> - 这其实也是微前端、插件化架构里常见的"故障隔离"思想

### 最后的小建议

- **提前演练一遍**：对着镜子或者找同学听你讲一遍，掐一下时间
- **准备好环境**：答辩前把 Ghost 启动好，页面打开，后台登录好
